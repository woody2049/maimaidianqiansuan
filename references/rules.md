# 规则详解

## 1. 项目缘起

在麦当劳点单时，三件事互相打架：预算有限、优惠券有门槛、营养目标（热量 / 蛋白质）又要顾。菜单上 30 多件餐品，人脑很难同时算清「哪种搭法最便宜」「哪种最贴合蛋白质目标」「哪种吃得最满足」。

「麦麦点前算」把这件事做成一次计算：给定条件，直接给出三组**已经卡过预算和营养**的搭配，每组都能照着在官方 App 里加购。它不做推荐玄学，只做穷举 + 打分 + 硬条件过滤。

产出三组，是因为「划算 / 营养 / 好吃」本质是三种取舍，合成一个「最优解」会掩盖掉权衡。

## 2. 输入格式

### 2.1 字段定义

```json
{
  "budget": 40,
  "nutrition": "any",
  "pickup": "pickup",
  "want": ["spicy", "friesM"],
  "avoid": [],
  "coupon": "prefer",
  "store": {"delta": 0, "soldout": []},
  "weekday": 1
}
```

| 字段 | 类型 | 约束 | 缺省 |
|---|---|---|---|
| `budget` | number | 12–80，超出则截断 | 40 |
| `nutrition` | enum | `any` / `low` / `protein` / `balanced` | `any` |
| `pickup` | enum | `pickup` / `delivery` / `drivethru` | `pickup` |
| `want` | string[] | 餐品 id，最多 3 个，去重 | `[]` |
| `avoid` | string[] | 餐品 id，无上限 | `[]` |
| `coupon` | enum | `prefer` / `normal` / `none` | `prefer` |
| `store.delta` | number | 门店价格档，通常 −1 ~ +1.5 | 0 |
| `store.soldout` | string[] | 该店停售的餐品 id | `[]` |
| `weekday` | number | 0=周日 … 6=周六，影响周二 88 折 | 当天 |

约束校验：
- `want` 里同一类目最多 1 个（必吃 2 个主餐会导致凑不出套餐）。
- `want` 与 `avoid` 不允许交集；交集时以「必吃优先」并向用户说明。
- 未知餐品 id 直接报错，不做模糊匹配。

### 2.2 命令行

```bash
python3 scripts/meal_planner.py \
  --budget 40 --nutrition any --pickup pickup \
  --want spicy,friesM --avoid salad \
  --coupon prefer --store-delta 0 --soldout mcflurry \
  --weekday 1 [--json] [--list-menu]
```

`--json` 输出 `{feasible, totalPlans, inBudget, poolSize, decks{budget,nutrition,taste}[], conflicts[], actions[]}`。

## 3. 预算、偏好与营养的处理

### 3.1 预算

预算作用于**实际应付**，不是总价：

```
总价   = Σ 餐品单价（基础价 + 门店差价，保留 2 位）
优惠   = max(各券优惠)，且 ≤ 总价；只取一张，不叠加
配送费 = 外送 ? (券后金额 ≥ 39 ? 0 : 6) : 0
应付   = 总价 − 优惠 + 配送费
```

判定：`应付 ≤ 预算 + 1e-6` 才算「预算内」。超预算的组合不进候选池，但仍保留在扫描结果里，供无解诊断算「差多少钱」。

### 3.2 必吃与忌口

- **必吃**：先锁定，直接占用对应类目。若必吃 1 主餐 + 1 小食，则穷举时主餐、小食不再选别的，只剩饮品/甜品可补。必吃项在当前门店或渠道点不到时，整单直接判无解（不是降级成别的餐品）。
- **忌口**：穷举前从菜单剔除，等价于该餐品不存在。全部主餐被忌口时判无解。
- 换门店/换取餐方式后，点不到的必吃项会被自动移除并提示。

### 3.3 券

| 券 | 类型 | 规则 |
|---|---|---|
| 随心配 1+1 | `pair` | 指定可配对餐品里挑最贵的 2 件，合计改价 13.9 |
| 组合券立减 6 | `combo` | 同时含主食 + 小食 + 饮品，减 6 |
| 满 30 减 5 | `threshold` | 总价 ≥ 30，减 5 |
| 满 45 减 8 | `threshold` | 总价 ≥ 45，减 8 |
| 麦乐鸡 10 块立减 5 | `item` | 含麦乐鸡 10 块，减 5 |
| 新客立减 3 | `flat` | 无条件减 3 |
| 周二会员日 88 折 | `rate` | 仅周二，按总价 × 0.12 减 |

券偏好三档：
- `prefer`：券参与打分（优惠权重 ×1），会为了用券接受多一件；
- `normal`：券照算金额，但打分里优惠权重 ×0.2，不为用券改变搭配；
- `none`：券池清空，按原价计算。

### 3.4 营养

营养参考是**硬门槛**，不是加分项：

| 参考 | 目标 | 通过条件 |
|---|---|---|
| 不限 | 720 kcal / 28g | 恒真 |
| 低卡 | 520 kcal / 26g | kcal ≤ 600 |
| 高蛋白 | 820 kcal / 42g | protein ≥ 42g |
| 均衡 | 700 kcal / 30g | 450 ≤ kcal ≤ 900 |

放宽顺序用于「无解时给建议」：`protein → balanced → any`、`low → any`、`balanced → any`、`any → 无`。

每日参考值（用于营养格里的百分比）：热量 2000 kcal、蛋白 60g、脂肪 65g、钠 2000mg。

## 4. 组合筛选与排序

### 4.1 筛菜单

```
菜单 = 官方菜单（若已同步） 否则示例菜单
剔除：该店停售
剔除：当前渠道不售（按名称匹配）
外送：/冰淇淋|麦旋风|新地|圆筒|沙拉/
得来速：/冰淇淋|麦旋风|新地|圆筒/
价格 = 基础价 + 门店差价
```

### 4.2 穷举

```
pool   = 菜单 − 忌口
forced = pool ∩ 必吃
rest   = pool − forced

若 forced 已有主餐 → 主餐位只有 1 种选择（空）
否则主餐位 = rest 的全部主餐
小食/饮品/甜品位 = [空] + 对应类目（若 forced 已占该类目，则只有空）

枚举 主餐 × 小食 × 饮品 × 甜品：
  件数 ∈ [2,4] 且至少 1 道主餐
  签名 = 排序后的餐品 id 拼接 → 去重
```

### 4.3 卡三道硬条件

```
组合总数     = 全部枚举
预算内       = 应付 ≤ 预算
达标         = 营养硬条件通过
候选池       = 预算内 ∩ 达标（必吃点不到时强制为空）
```

### 4.4 打分

```
热量贴合 = clamp(1 − |kcal − 目标kcal| / (目标kcal × 0.62), 0, 1)
蛋白达标 = clamp(protein / 目标protein, 0, 1)
营养贴合 = 0.6 × 热量贴合 + 0.4 × 蛋白达标

性价比   = clamp((kcal / 应付) / 32, 0, 1)
优惠力度 = clamp((优惠 / 总价) / 0.36, 0, 1)
满足感   = clamp((饱和脂肪 − 3) / 7, 0, 1)
完整度   = 有小食 0.5 + 有饮品 0.5（×0.03 加成）

分数 = w_fit × 营养贴合 + w_value × 性价比 + w_disc × 优惠力度
     + w_sat × 满足感 + 完整度 × 0.03

若 应付 > 预算：分数 −= 0.4 + (超支 / 预算) × 1.1
券偏好非 prefer：w_disc ×0.2
营养参考非 any：w_fit ×1.15
```

### 4.5 三组与排序

| 组 | w_fit | w_value | w_disc | w_sat | 门槛 | 主排序 | 次排序 |
|---|---|---|---|---|---|---|---|
| 预算优先 | .18 | .48 | .24 | .10 | .55 | 应付升序 | 分数降序 |
| 营养参考优先 | .60 | .16 | .12 | .12 | .50 | 营养贴合降序 | 分数降序 |
| 口味优先 | .14 | .14 | .12 | .60 | .50 | 满足感降序 | 应付升序 |

每组流程：

1. 对候选池全部打分，取分数分位门槛 `max − (max−min) × (1−gate)`，保留过线者；全不过线则用全量。
2. 按主排序排列，依次装叠，最多 5 个。
3. 去重：签名相同跳过；与已入叠方案「太像」也跳过。
4. 若首选已被别的组占用，用全量候选补位；仍冲突则把叠内第一个未占用的方案轮转到队首。
5. 三组首选保证互不相同；内容完全收敛时只展示一组，并注明「和上面某组收敛到同一种搭配」。

**太像的判定**：
- 主餐相同且主餐非必吃：
  - 任一方没有配餐 → 太像；
  - 双方都 ≥2 件配餐 → 太像（只换配餐差别太小）；
  - 否则配餐有交集 → 太像。
- 主餐不同：配餐交集数 ≥ 较少一方的件数 → 太像。

## 5. 价格核验

有真实门店（已选官方门店 + 菜单已同步）时，每张展示中的方案都核一遍：

1. 把方案里每件餐品映射到官方 `productCode`（按名称匹配同步下来的菜单）。
2. 调 `calculate-price`，参数 `storeCode / orderType / beType / needTableware:false / items[{productCode,quantity:1}]`。
3. 取官方 `originalPrice`（无则 `price`）与本地**总价**比较：
   - 差值 < 0.01 → `ok`，显示「原价合计和本地估算一致」；
   - 否则 `diff`，显示「比估算多/少 ¥X，以官方结果为准」。
4. **不比「应付」**：本地券是示例券，官方结算不会叠加，比应付会系统性偏差。核价结果里会写明这句。
5. 同一套餐 10 分钟内不重复请求；失败可手动重试。

状态汇总在结果页顶部：`ok`（全部一致）/ `diff`（有差异）/ `fail`（没核成功）/ `off`（未接官方数据，仅本地估算）。

## 6. 无解处理

### 6.1 先定位冲突

按顺序检查，命中即写入冲突清单（可多条）：

| 检查 | 冲突标签 | 典型文案 |
|---|---|---|
| 必吃项点不到 | 餐品 | 「麦旋风」这家门店停售 / 外送不售 |
| 主餐全被忌口 | 餐品 | 主餐被忌口排光了 |
| 必吃占满 4 件 | 组合 | 按现在的必吃项凑不出套餐 |
| 预算内一个组合都没有 | 预算 | 预算 ¥25 装不下任何组合，最便宜要 ¥42，差 ¥17 |
| 预算内有组合但营养不达标 | 营养 | 预算内蛋白质最高 31g，离目标 42g 差 11g |
| 以上都不成立 | 条件 | 这几项条件凑不到一起 |

### 6.2 六个调整方向

每个方向都必须**先试算确认改完真的有解**，才给可点按钮；给不出就写清为什么不行（卡点不在这一项 / 超过上限 / 已经最宽）。

1. **增加预算**：依次试 `ceil(最便宜达标价)`、`ceil(最便宜价)`，取第一个能出方案的金额，上限 ¥80。
2. **放宽营养参考**：按放宽顺序试下一档，可连带微调预算。
3. **替换餐品**：把某个必吃项换成同类里更便宜/更低卡的（最多试 12 个候选）。
4. **去掉一个餐品**：按价格从高到低试删必吃项；没有必吃项时，退而放开一个忌口的主餐。
5. **更换取餐方式**：只改取餐方式，不连带改预算。
6. **更换城市/门店**：先同城换店（按距离），再按「价格档 + 停售组合」签名去重，最多试 20 家外城门店。

试算函数（`fixFor`）的兜底链：`原补丁 → 逐档放宽营养 → 营养放到不限 + 预算提到最便宜组合`。任何一步成功，就把「连带改了什么」写进按钮文案。

### 6.3 输出

- 不显示任何方案卡，底部「换一组方案 / 保存方案 / 前往 App」全部禁用。
- 冲突卡片说明卡在哪，附带具体数字（差多少钱、差多少克蛋白）。
- 六个按钮按「最可能有效」排序，可点的标「重算 ›」，不可点的标「不可用」并说明原因。

## 7. 使用限制与数据说明

- **示例数据**：30 件餐品、7 张券、320+ 城市门店均为演示；门店名、距离、出餐时间、停售都是构造的。
- **真实数据**：只来自麦当劳官方 MCP（菜单 / 价格 / 营养 / 门店券）。官方菜单解析需按 `data.categories[].meals[].code` + `data.meals[code]` 码表拼装，识别不足 8 件时回落到示例菜单。
- **营养**：估算值，仅作点餐参考，不构成饮食或健康建议；文案禁止出现减重、降糖、治疗等功效表述。
- **外送**：官方接口拿不到收货地址，真实门店只支持到店自取 / 得来速；外送用示例数据。
- **不代下单**：不登录麦当劳账号、不下单、不支付；跳转官方 App / 官网由用户自己完成。
- **隐私**：不收集姓名、电话、地址；未登录时规则与方案只存本机 localStorage（最多 50 条）。
- **Token**：预置 MCP Token 写在页面源码里，公开部署时可见；生产环境应移到服务端环境变量。
